The SNES, as EarthBound sees it

A map of the hardware our Nim emulator reproduces — memory layout, ROM & SRAM storage, the MMIO registers, and the three processors — scoped to exactly what EarthBound (U) touches.

The Super Nintendo is three processors sharing a 24-bit address space: the 65816 main CPU, the PPU (picture) and the APU (sound, its own SPC700 CPU). EarthBound is a HiROM, 3 MB (24 Mbit) cartridge with 8 KB of battery-backed SRAM. Everything below is what decompbound implements on demand — registers the game actually uses get real behavior; everything else reads open-bus zero.

The 24-bit address space

An address is bank:offset — an 8-bit bank ($00–$FF) and a 16-bit offset ($0000–$FFFF), giving 16 MB of addressable space. The SNES fills it with a mix of ROM, RAM, and hardware registers. Here is the whole space, colored by what lives where:

How the ROM is stored — HiROM

The cartridge is a mask-ROM chip holding EarthBound's ~3 MB of code, graphics, music and text. "HiROM" is the mapping that decides how that linear chip appears in the address space. Unlike LoROM (which only exposes the upper 32 KB of each bank), HiROM maps full 64 KB banks, so the ROM sits contiguously in $C0–$FF (its home), mirrors into $40–$7D, and is also visible in the upper half ($8000–$FFFF) of the system banks $00–$3F / $80–$BF.

File offset → SNES address

A byte at file offset N appears at multiple SNES addresses. Its canonical HiROM home:

snesAddr = $C00000 + N

…and mirrored so the same byte is reachable from the fast banks and the $8000–$FFFF windows. decompbound copies the ROM into every mirror at boot so any legal address just works.

The vectors

On power-on the 65816 reads its reset vector from $FFFC/$FFFD (bank 0) and jumps there. NMI (vblank), IRQ, BRK and COP vectors sit just below at $FFE0–$FFFF. For HiROM these come from the very top of the ROM image.

A 512-byte "copier header" sometimes precedes the ROM data in a dumped file. decompbound detects it (fileSize mod 1024 == 512) and strips it so offsets line up.

WRAM — the 128 KB work RAM

Two full banks, $7E and $7F, are 128 KB of general-purpose RAM. This is where the game's live state lives: the party, the map, flags, and — relevant to us — the buffers EarthBound's effects churn through. The Giygas "death static," for instance, is generated procedurally into WRAM at $7F0200+ each frame, then DMA'd to video RAM. The bottom 8 KB ($7E:0000–$1FFF) is the hot RAM mirrored into every bank's $0000–$1FFF for one-byte-shorter addressing.

SRAM & the save format

An 8 KB battery-backed static RAM holds the save. On real hardware a coin-cell keeps it alive between power-ups; in decompbound it's persisted to a gitignored <rom>.srm file (real non-volatile storage the way a dead-battery cart never had). It's mapped at $6000–$7FFF in banks $20–$3F (and the $A0–$BF fast mirror) — EarthBound's anti-piracy check probes exactly this size and mirroring.

We reverse-engineered part of the save format live, by watching bytes move as real stats changed across saves, deaths, and bank withdrawals. Confirmed offsets:

The 65816 main CPU

A 16-bit descendant of the 6502. Two quirks dominate EarthBound's code:

  • M and X flags — the accumulator and index registers each toggle between 8- and 16-bit width at runtime via the M and X status bits. The same opcode reads a different number of bytes depending on them, so a disassembler must track flag state, not just decode bytes.
  • Emulation mode — it powers on pretending to be a 6502 and the game switches to native mode early. HiROM 24-bit addressing (data-bank + program-bank registers) does the rest.

decompbound's core is verified instruction-by-instruction against the TomHarte SingleStepTests vectors — every opcode, every addressing mode.

The PPU — building the picture

The picture processor composites layers into a 256×224 frame from three memories: 64 KB VRAM (tiles + tilemaps), 512 B CGRAM (256 BGR555 palette colors), and 544 B OAM (sprite table). EarthBound uses:

Layers & priority

Up to 4 background layers + sprites, ordered by a per-tile/per-sprite priority. The menu & battle UI ride high-priority BG3 so text sits over everything.

Color math

Add or subtract a "subscreen" (or fixed color) from the main image — half-transparency, flashes, and the Giygas red static are all color math.

HDMA

DMA that fires once per scanline, rewriting registers mid-frame. It builds gradients, and splits the battle screen into horizontal bands (menu / battlefield / status).

Windows

Rectangular masks whose edges HDMA can move per scanline — the black iris/shutter that irises in around a scene is a window tracing a shrinking circle.

The APU — a whole second computer for sound

Sound is offloaded to an entirely separate CPU, the SPC700, with its own 64 KB of RAM and the S-DSP that mixes 8 voices of ADSR-enveloped BRR samples. The main CPU can't touch it directly — it speaks through the 4-byte $2140–$2143 mailbox.

At power-on a tiny 64-byte IPL boot ROM runs on the SPC700 and performs the upload handshake: the game streams its sound driver + music/sample data across the mailbox, then tells it to play. decompbound runs the real SPC700 + DSP + IPL live in the bus, so the note sequences and the instrument samples always stay coherent — the same reason the stereo pan of Pokey's door-knock shifts correctly when you change floors.
