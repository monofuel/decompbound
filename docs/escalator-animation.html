How escalators move

The steps roll endlessly, but the escalator never actually scrolls off the screen. Two SNES tricks pull this off — and neither one moves a single pixel of geometry.

TL;DR. An escalator is a fixed patch of background tiles. The illusion of motion comes from changing what those tiles look like every frame — either by swapping the tile graphics (CHR animation) or by rotating the palette colors (palette cycling). The tilemap positions never change; only their appearance does.

The effect. Steps stream upward forever. Watch the geometry — nothing is actually being drawn "moving." (CSS approximation of the illusion.)

Two ways to fake motion

Method 1

CHR / tile-graphics animation

The tilemap keeps the same tile indices at the same positions, but the actual 8×8 pixel data for those tiles (the CHR in VRAM) is re-uploaded every frame or two via DMA. Frame 1 shows step-pattern A, frame 2 shows it shifted a few pixels, and so on — looped.

Cost: a small VRAM DMA each frame. Flexible — the steps can shift by any amount and even change shape. This is the usual choice for escalators & conveyor belts.

Method 2

Palette cycling (color rotation)

The tile graphics stay fixed. Instead, the escalator is drawn using a small band of palette indices, and the colors assigned to those indices (in CGRAM) are rotated each frame. Draw diagonal stripes with a repeating color ramp, rotate the ramp, and the stripes appear to march.

Cost: a handful of CGRAM writes — cheaper than a CHR DMA. Classic for water, lava, and stripe-based conveyors. The trade-off: motion is locked to the palette pattern.

Same look, driven by rotating colors instead of moving pixels.

Both produce the identical on-screen result; they differ only in what the game rewrites each frame — VRAM tile data vs. CGRAM palette entries. From a black-box view you can't tell them apart; from inside the machine (or a trace) they're obviously different.

What we found (reverse-engineered from the ROM). EarthBound has both mechanisms wired, both driven from the NMI (vblank) handler:

  • Palette cycling — a CGRAM DMA path at $C081C8: writes rotating colors to $2122, with source/size/offset from a table at $C08F92.
  • CHR animation — a VRAM-DMA queue at $C0823C: 8-byte records in WRAM at $0400 (config index + size + 24-bit source + VMADD), a config table at $C08FB0, re-uploading tile graphics to $2118 — fed from the effect command-lists at $C59400+ (dispatcher near $C59894).

Both were confirmed in make trace logs (per-frame $2122 CGRAM and $2118 VRAM DMAs). Which one escalators specifically use is still open — the dig couldn't reach an active escalator headlessly. The clean confirmation: grab a save-state at a Fourside escalator and let the trace tool watch one frame (a VRAM DMA to the escalator tiles = CHR animation; rotating CGRAM = palette cycling). Same trick that's been cracking everything else.

How our emulator handles it

Either technique "just works" if the emulator is faithful, because both are ordinary hardware writes we already model: a CHR DMA lands new tile data in VRAM (and renderScanline reads it next frame), while a palette write updates CGRAM (and the composite picks up the new colors). No special escalator code — if the steps move on hardware, they move for us, as long as our DMA and CGRAM timing are right. If an escalator ever looked frozen or wrong in decompbound, that'd point at a per-frame DMA or palette-update bug, not at anything escalator-specific.
